## 资源按 GPU 比例统一分配

当前实机：6 块 RTX 6000 Ada、64 个物理 CPU 核心（无 SMT），CPU 编号 0–63。

CPU 核心配额采用 `floor(64 × 本任务 GPU 数量 / 6)`。向下取整保证不超出所占服务器比例。

| GPU 数量 | CPU 核心上限 |
| ---: | ---: |
| 1 | 10 |
| 2 | 21 |
| 3 | 32 |
| 4 | 42 |
| 5 | 53 |
| 6 | 64 |

配额属于整个实验进程树。例如两卡任务的 21 核由主进程、两个 worker、tokenizer、DataLoader 和 BLAS/PyTorch 线程共同使用，不是每个 worker 各用 21 核。启动器通过 Linux CPU affinity 限制可执行的核心集合，子进程和线程继承；环境变量进一步限制默认线程池规模。它不只是设置 OMP 变量，也不修改系统服务或别人的任务。

新增正式入口 `tools/run_with_resources_v2.py`（`v1` 保留为初版记录，后续统一使用 `v2`）：

- 必须显式指定物理 GPU 编号，通过 UUID 设置 `CUDA_VISIBLE_DEVICES`，子程序从逻辑 GPU 0 开始编号。
- 自动读取实机 CPU/GPU 总数，计算整数 CPU 配额，不硬编码 64/6。
- 检查选中 GPU 是否明显被占用；当前默认拒绝显存已用超过 1,024 MiB 或 GPU 利用率超过 10% 的设备。
- 同一用户、同一主机、经此入口启动的并发任务，共享锁保护的资源记录，避免 GPU 和 CPU 集合重叠。记录存于 `/tmp/neurobypass-resources-<uid>/`。
- 限制整个命令进程树的 CPU affinity，设置 OMP/MKL/OpenBLAS/NumExpr/Rayon 线程数，禁用 tokenizer 隐式并行。
- 将配置、合并标准输出日志与退出状态存到新运行目录，已有目录会报错，避免覆盖历史结果。
- 信号转发到实验进程组，退出后释放本入口的预约记录。

这个入口是本项目的合作式资源分配器，不是全服务器调度系统。其他用户或绕过入口启动的任务不受它限制；GPU 空闲检查也不等于系统级独占。CPU 配额表示最多在哪些核执行，不保证独占核心或一定占满配额。CUDA 可见性限定可选 GPU，实际多卡工作仍需要两进程或 torchrun，单卡程序不会自动变成多卡。

## 使用方法

从项目目录运行，启动器本身仅依赖 Python 标准库和 `nvidia-smi`。

```bash
cd /home/liushenyu/test/NeuroBypass

# 只查看资源计划，不启动计算、不预约 GPU/CPU。
PYTHONDONTWRITEBYTECODE=1 python tools/run_with_resources_v2.py \
  --gpus 1,3 --dry-run

# 使用两块指定 GPU，整个进程树限制在 21 个 CPU 核心内。
PYTHONDONTWRITEBYTECODE=1 python tools/run_with_resources_v2.py \
  --gpus 1,3 --run-dir runs/my_new_experiment_001 -- \
  /home/liushenyu/anaconda3/envs/traindata/bin/python your_new_program.py
```

两卡 DDP 训练应在同一入口后执行 `python -m torch.distributed.run --standalone --nproc_per_node=2 ...`，读取 `LOCAL_RANK` 选择逻辑 GPU。独立评测则按逻辑 GPU 0、1 分发不重叠数据分片，每卡加载一份 OPT-13B，避免推理阶段不必要的梯度同步。两卡时线程池默认每个 worker 10 线程；进程树总 affinity 仍是 21 核。新增程序应读取 `NEUROBYPASS_CPU_COUNT`，让 DataLoader worker 数与计算线程一起服从预算。

当前不自动挑 GPU。显式指定编号可以避免误用其他人的资源；每次启动会重新检查。2026-11-03 本次检查时 0、2 已有其他进程占用，1、3 空闲，后续以实时检查为准。

## 推进顺序和判断依据

### 第一步：两卡修正评测，先回答“已有模型学到了什么”

资源：**2 GPU / 21 CPU 核心**。先做独立分片推理，暂不重训。

新增评测程序需要固定：同一测试输入、同一 K、相同保护层 0 和 1、相同 tokenizer 和任务打分规则；所有 checkpoint 缺失必须报错；输出逐样本结果、实际剪枝组合、模型/程序哈希与资源记录。先选 K=6 和 16，之后补 K=12。使用 last-token float32 KL 做初查，同时增加所有有效 token 的平均 KL、语言建模损失，避免只拟合一个位置。

比较以下方案：

1. 完整 OPT-13B，作为质量参考。
2. 最新 Transformer，修正为剪最低保留分数的 K 层；原反向策略仅作为错误诊断。
3. 旧固定 6 层 RL（只在其支持的 K=6 下评价，不强行扩展到 16）。
4. 从独立校准集搜索得到的固定静态组合；原手选组只作历史参考。
5. 随机组合，保护范围和 K 相同，多次采样。

初查取 **256 个互不重叠的独立 C4 文本块**，明确排除训练用的块；校准数据与测试数据分离。在本地语料可以追踪来源的情况下选择未被旧生成器访问的区间，并保存原始 byte/token offset 与分组 ID。随后在完整 PIQA validation 上用一致的选项似然和长度归一化协议验证，先保留逐题结果再讨论均值。

交付：质量表、mask 众数占比、每层选择频率、错误样本和不同输入上的组合变化。不根据 200 题里两三题的差异宣称优势。

### 第二步：小样本检验动态剪枝的收益空间

资源仍为 **2 GPU / 21 CPU 核心**。先选上述独立测试中的 32 个块，计算逐样本贪心参考，必要时再扩大；逐样本搜索不使用待评测任务答案，静态组合只在校准集选择。该参考是近似搜索结果，不称为全局最优或严格上界。

看三个量：强静态组合的质量、逐输入贪心能改善多少、Router 实现了其中多少改进。若逐输入参考也没有稳定优势，则当前模型/预算下输入动态选择的价值可能有限；若参考明显较好而 Router 跟不上，则优先改善数据与学习目标。

同时加入真实输入、打乱输入与决策对应、固定输入/仅给 K 的消融。打乱输入导致决策与当前输入不匹配，必须在同一批测试样本与相同 K 下比较。**输出会变化不能单独证明动态选择有收益。**

### 第三步：按独立文本重新构建训练数据

通过前两步后再投入标签生成和重训，继续只新增 `v4` 等独立版本。

先做 **至少 1,000 个不同文本块** 的试验数据，每个块只取 1–2 个长度，按文档或块分组划分 train/val/test；记录全部来源和 split。保证“1,000 条样本”对应足够多独立内容，避免再由几十个块生成大量嵌套前缀。

标签生成继续记录每步选择与代价，但改用 float32 分布计算 KL、明确有效 token、真正绕过选中层、finally 恢复、完整异常日志和可校验断点续跑。先生成 32 块测量每块耗时和显存，再估算总成本。贪心 16 步有数百次候选前向，不直接承诺几小时完成。

先从两卡试验规模开始；若明确有收益并需要加速，扩大到 **4 GPU / 42 CPU**，按块分片生成，各 worker 有独立输出目录。只使用当时可用且已分配的 GPU。

### 第四步：重训和自适应 K 分开做

先用两卡、21 核完成“给定 K 选组合”的 SFT，并用按组独立验证集挑 checkpoint。MLP 与 Transformer 使用各自明确且一致的特征，比较相同数据与预算。只有 SFT 受限的原因已量化，才继续 RL；RL 要处理右 padding、exact-K 动作和奖励一致性。

固定 K 组合选择站得住后，再训练/校准质量风险或深度选择器，让输入选择 K，并允许 K=0。阈值来自独立验证集；目标应是给定质量下降约束下尽量少计算，而不是手写 margin 映射。最后再做真实执行成本、prefill/decode、Router 开销和 KV cache 的单独评测。
